# Архитектурная записка

## 1. Обработка вебхуков и Exactly-Once под гонками
- **Идемпотентность платежей:** Все входящие события фиксируются в таблице `payment_events` с первично ключом `event_id`. Повторный запрос с тем же `event_id` вызывает `ON CONFLICT (event_id) DO NOTHING`, и приложение сразу возвращает ошибку о том, что событие уже обработано (`event already processed`).
- **Блокировка заказов:** Изменение заказа выполняется в единой транзакции с `SELECT ... FOR UPDATE` по таблице `orders`. Это исключает race condition при одновременном приходе нескольких разных вебхуков по одному заказу.

## 2. Устойчивость интеграций и ловушка таймаута
- **Идемпотентность выдачи:** При вызове поставщика генерируется `request_id` вида `reaper-ord.ID`.
- **Ловушка таймаута:** Заглушка поставщика проверяет таблицу `keys` по полю `request_id` через метод `GetByRequestID`. Если ключ уже зарезервирован, возвращается старый код без резервирования нового.
- **Выдача ключа без Race Condition:** Выдача ключа из базы производится атомарным запросом `UPDATE keys SET status = 'issued', request_id = $1 WHERE id = (SELECT id FROM keys WHERE sku = $2 AND status = 'available' LIMIT 1 FOR UPDATE SKIP LOCKED)`. Использование `SKIP LOCKED` гарантирует, что две параллельные выдачи никогда не заблокируют один и тот же ключ.
- **Fallback A/B:** При сбое или отсутствии остатка у поставщика A клиент выполняет повторные попытки (retries) и переключается на поставщика B.

## 3. Сверка и фоновое восстановление (Reaper)
- **Reaper Worker:** Фоновый воркер периодически запрашивает из таблицы `orders` заказы в статусах `paid`, `out_of_stock`, `delivery_failed` и повторно отправляет их на выдачу поставщику.
- **Reconciliation API:** Эндпоинт `GET /api/reconcile` возвращает массив повисших заказов и их количество.
- **Денежный журнал (Ledger):** Таблица `payment_events` со связкой `FOREIGN KEY (order_id) REFERENCES orders(id)` выступает строгим журналом финансовых транзакций.

## 4. Спроектированная схема каталога под нагрузкой
Для быстрого отображения витрины остатков при тысячах SKU используется оптимизированный составной индекс по твоим существующим таблицам `keys` и `orders`.

### Оптимальные индексы
```sql
-- Частичный индекс только по доступным ключам для моментального поиска/подсчета
CREATE INDEX idx_keys_sku_available ON keys (sku) WHERE status = 'available';

-- Индекс по заказам для ускорения поиска зависших статусов
CREATE INDEX idx_orders_status ON orders (status) WHERE status IN ('paid', 'out_of_stock', 'delivery_failed');

```

### Запрос витрины и объяснение плана (EXPLAIN)

Для вывода каталога с актуальными остатками:

```sql
SELECT 
    k.sku, 
    COUNT(k.id) AS stock_count
FROM keys k
WHERE k.status = 'available'
GROUP BY k.sku;

```

**План выполнения:**
* **Index Only Scan:** Благодаря частичному индексу `idx_keys_sku_available`, СУБД читает только сам индекс без обращения к страницам самой таблицы `keys`.
* **Быстрая фильтрация:** Пропускаются миллионы уже проданных (`status = 'issued'`) ключей. Время выполнения запроса остается постоянным независимо от общей величины таблицы `keys`.
* **Кэширование:** При сверхвысоких нагрузках витрина кэшируется в Redis на 1-3 секунды, либо счетчики свободных SKU ведутся асинхронно.
